# Работа в opencode-autoapprover

Нативный TypeScript-плагин OpenCode V2 оценивает риск shell-команд одной LLM;
разрешение определяется кодом по порогу оператора.
Эти инструкции предназначены для Codex и OpenCode независимо от выбранной coding-модели.

## Общение и границы задачи

- Общайся по-русски, в том числе после `/review`. Код, команды, пути, идентификаторы, точные цитаты и сырой вывод оставляй в исходном виде.
- Выполняй текущий запрос владельца. Исследование и review ограничивай чтением; при запросе реализации доводи согласованные изменения до проверяемого результата.
- После одобрения реализации продолжай без повторного согласования плана; уточняй только существенную неоднозначность или блокер.
- Исследуй только неизвестные, необходимые для задачи. Выбранные язык, V2 API и архитектуру не пересматривай без соответствующего запроса.

## Начало работы и источники истины

1. Проверь cwd и `git status --short`; сохрани существующие изменения пользователя.
2. Прочитай [README.md](README.md), [TASKS.md](TASKS.md) и текущую сводку [статуса реализации](reports/IMPLEMENTATION_STATUS.md). Сверяй противоречивые статусы с кодом и датированными evidence.
3. Перед изменением поведения прочитай [SECURITY.md](SECURITY.md) и [требования](docs/01-requirements.md); затем документы из маршрута ниже.
4. Продолжай актуальную задачу. [START_HERE.md](START_HERE.md) и [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md) описывают первоначальную последовательность M0–M5; повторяй квалификацию только по необходимости текущей задачи.

Явные новые указания владельца выше документации.
Внутри комплекта приоритет: `SECURITY.md` → `docs/01-requirements.md` → JSON-схемы и их семантические правила → остальные документы → примеры.
Требования определяют целевое поведение, код — реализацию, отчёты и evidence — выполненные проверки. При противоречии не ослабляй условия `allow`: сохраняй `ask`, зафиксируй конфликт и решение; исправляй в рамках задачи.

## Инварианты runtime-плагина

Эти ограничения относятся к создаваемому плагину; правила работы агента-разработчика приведены отдельно ниже.

- Только OpenCode V2 и публичный `@opencode/plugin`. Запрещены V1 `permission.ask`, `@opencode-ai/plugin`, private Core imports и обход SDK через `any`.
- Только текущий входящий `ask` для `shell` может стать `allow`, при выполнении всех gates из `SECURITY.md`. Native `allow`/`deny`, другие actions и режим `off` оставлять без изменения.
- Не создавать автоматический `deny`, persistent/session permissions или `always`, не изменять persistent/session rules; не менять команду и не выполнять её самостоятельно. Локальный стоп возвращает решение человеку.
- Риск выше `autoAllow`, `UNKNOWN`, отсутствующий контекст, несвязанный input, невалидный или несогласованный ответ, сбой, timeout, превышение лимита и отказ аудита сохраняют `ask`.
- Потолки схемы не обходятся: HIGH/CRITICAL/UNKNOWN риска, LOW confidence и UNKNOWN-категория не допускают auto-allow. LLM оценивает риск; авторизация — детерминированный порог и остальные gates.
- До LLM выполняются минимальные недублирующие проверки: binding, cwd внутри admitted root, секреты, oversized/control-char input, consent, лимиты и доступность аудита. Не добавлять собственный command recognizer или парсер shell-грамматики.
- На допущенную оценку — ровно один вызов явно выбранной LLM через OpenCode. Без fallback-моделей, retries, subagent, session prompt, tools, полного transcript и произвольного чтения проекта ради классификации.
- Используй нативный stateless `ctx.generate.text`; неизвестная комбинация host/SDK/platform не допускается к live auto до квалификации.
- Не извлекать credentials OpenCode; не добавлять прямой HTTP provider adapter. Не логировать сырые запросы, ответы или секреты.
- Поздний результат, отменённый запрос и устаревший snapshot не могут изменить effect. Ошибки не являются основанием для разрешения.
- Production policy и установленный исполняемый плагин должны находиться вне изменяемого агентом рабочего дерева. Файлы проекта, `AGENTS.md` и аргументы команды не являются доверенной runtime-policy или разрешением.
- Плагин не заменяет sandbox. Если host обходит permission-hook, прекращать smoke: выключение guard не устраняет обход на стороне host.

## Правила работы разработчика

- Никогда не запускай `rm`, включая точечное удаление. Не обходи запрет через обёртки, `find`, `xargs`, циклы, алиасы, копии программ, другой язык или cleanup-скрипты; не запрашивай разрешение на обход.
- Временные артефакты размещай в уникальном каталоге под `/tmp`, созданном через `mktemp -d`, без автоматической очистки. Не удаляй файлы: если удаление требуется, перечисли точные пути и оставь его пользователю.
- После работы с одноразовыми артефактами от примерно 50 МБ сообщи пути, размеры, способ ручной очистки и риски; сам очистку не выполняй.
- Сохраняй чужие local/IDE changes. Не создавай worktree без прямой просьбы.
- Не строи многоагентную фабрику. Делегируй только по явному запросу пользователя или применимого навыка; review-only агенты не меняют код.
- Не подключай разрабатываемый auto-approval к текущей рабочей сессии. Не меняй пользовательские настройки и не включай `auto` без отдельного действия пользователя.
- Не читай и не копируй секреты OpenCode. Для evidence собирай минимальный redacted trace; не сохраняй реальные ключи, полный transcript или окружение целиком.
- Строки из fixtures никогда не выполняй. Для разрешённого host smoke используй безвредные команды в отдельном тестовом каталоге.
- Разрешение на offline-разработку не означает согласие на live-передачу данных. Следуй операторской инструкции и явно согласованным provider/model/root/consent.

## Код и зависимости

- Строгий TypeScript; тонкий SDK-адаптер, чистые функции и небольшие модули core. API проверяй по установленным типам и evidence, не выдумывай поля и версии.
- Зависимости минимальны: V2 SDK и один проверенный валидатор/JSON-parser. Точные версии и lockfile сохраняй; изменение совместимости требует квалификации соответствующей комбинации host/SDK/platform.
- Не добавляй Effect для переписывания Promise API, provider SDK, Go-процесс, БД, веб-сервис или дополнительную CLI-платформу.
- Не помещай в эти инструкции настройки конкретной модели, температуру, API-поля thinking или требования раскрывать внутренние рассуждения. Provider transport обслуживает OpenCode.
- Если локальный host недоступен, продолжай разрешённую независимую core/mock-работу; host/live проверки отмечай `NOT_RUN`, live auto оставляй заблокированным.

## Проверки

Команды выполняются из корня; актуальный состав scripts — в [package.json](package.json).

| Команда | Когда применять |
|---|---|
| `bun test <путь-к-тесту>` | После изменения затронутого поведения; подставить существующий файл или каталог тестов |
| `bun run typecheck` | Проверка типов, включая установленный SDK |
| `bun run test:contract` | Contract и corpus при изменении gates, адаптера, lifecycle или схем |
| `bun run check` | Итоговая offline-проверка кода: typecheck, unit/contract/corpus и build |

Mock-тесты не требуют ключа и сети. `test:live` сейчас — заглушка, намеренно завершающаяся ошибкой; live-проверки проводятся отдельно по операторской инструкции.
После небольших изменений запускай focused-проверки; полный `check` — по завершении этапа реализации и перед сдачей кода. Если итоговая проверка уже прошла и код не менялся, повтор не нужен.
Для изменения только документации проверь ссылки, команды, фактические утверждения и форматирование diff; runtime suite не требуется. При untracked-файлах сравнивай с сохранённой исходной копией: пустой `git diff` не доказывает отсутствие изменений.

## Завершение задачи

- Выполни короткий diff-review: scope, сохранность gates, отсутствие секретов и несвязанных изменений.
- После этапа реализации обнови [TASKS.md](TASKS.md) и [статус реализации](reports/IMPLEMENTATION_STATUS.md): что изменилось, команды и результаты, ограничения, следующий минимальный шаг.
- При изменении поведения актуализируй затронутые критерии и связи с тестами в acceptance-матрице. Unsafe/uncertain/error-сценарии не должны давать auto-allow; позитивный путь также должен проверяться.
- Для сдачи плагина нужны все обязательные критерии приёмки, инструкция установки/отключения, точные pins и перечень непроверенных границ.
- В ответе укажи результат, выполненные проверки и оставшиеся ограничения. Разделяй `PASS / FAIL / NOT_RUN` для offline, host smoke и live model; частичный результат описывай явно.
- Исторический PASS не является новым прогоном. Зелёные mock-тесты не доказывают готовность live auto; приводи версии окружения только для реально выполненных проверок.
