# Примеры, а не автоматически активируемые настройки

`guard.shadow.json` проходит структурную схему, но содержит placeholders и отключённое согласие на передачу. `guard.auto.json` показывает будущую активную конфигурацию и включает consent; **не использовать до host qualification и ручной проверки всех значений**. Оба файла отклоняются operational validation, пока есть `REPLACE_ME`.

Секция `escalation` опциональна (D3): без неё — одна модель и одна попытка. `escalation.allowedCategories` (D7) — надмножество `policy.autoAllow.allowedCategories` (нарушение → `CONFIG_INVALID`): расширенные категории (например `EXEC`) авторазрешаются только с вердикта ступени эскалации. Модель эскалации обязана отличаться от основной; актуальные диапазоны и дефолты — в `docs/05-configuration.md`.

Guard config сохраняется в глобальном каталоге пользователя по `docs/05`. OpenCode fragments вручную объединяются с собственным config; не заменять ими файл целиком и не стирать существующие deny.

Custom provider fragment нужен только для endpoint, ещё не настроенного в OpenCode. Он использует совместимый host runtime и ссылку на имя переменной окружения. Здесь нет реального API-ключа. Provider/model ID пользователь берёт из своей действующей конфигурации; примеры не утверждают наличие конкретного коммерческого тарифа/модели.

Никакой файл в этом каталоге не подключается через auto-discovery. Runtime код ещё предстоит создать.
