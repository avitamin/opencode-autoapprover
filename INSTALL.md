# Установка, включение и откат (операторская инструкция)

Практический runbook для `opencode-llm-approval` на фактических версиях проекта. Нормативная эксплуатационная документация — [docs/09-operations.md](docs/09-operations.md); здесь собраны конкретные команды и значения, проверенные на реальном хосте. Заменой вашего конфига эти файлы не являются.

## 1. Проверенные версии (pin)

| Компонент | Версия | Примечание |
|---|---|---|
| OpenCode host | **v2.0.18** | контрактовано в `compatibility/host-contract.json`; smoke P1/P2 дополнительно прошёл на v2.0.19 (авто-обновление desktop) — протокол в локальном evidence оператора; адресный smoke на v2.0.32 (Windows 11, standalone + живой Desktop-сервис) — PASS 19.10.2026 (D10) |
| `@opencode/plugin` (SDK) | **2.0.18** | точный pin в `package.json`; lockfile `bun.lock` |
| ajv | **8.20.0** | единственная runtime-зависимость кроме SDK |
| Bun (сборка/тесты) | **1.4.2** | не нужен на хосте после установки |
| TypeScript | **7.0.2** | только сборка |

Обновление любой из версий = новая сборка → короткая повторная квалификация (п. 5.4) перед возвращением `auto`.

## 2. Сборка и установка вне рабочего дерева

Устанавливаемая копия не должна лежать в репозитории, который редактирует агент.

```bash
# в клоне репозитория (однократно):
bun install
bun run check          # typecheck + 448 offline-тестов + build; без сети и ключей

# упаковка staged-копии вне рабочего дерева:
bun run build
bun scripts/make-package.ts --stage ~/.local/share/opencode-llm-approval-v2.8.3
cd ~/.local/share/opencode-llm-approval-v2.8.3/opencode-llm-approval
bun install --production
```

Упаковщик принимает только новый или пустой staged-каталог и не перезаписывает прежнюю сборку. При обновлении установленной копии сначала сравнивайте состав пакетов (старый dist + новый конфиг с новыми секциями → `CONFIG_INVALID` → все ask — обновляйте dist и конфиг вместе; протоколы обновлений — локальный evidence оператора).

Место установки по умолчанию — домашняя директория пользователя (`~/.local/share/`, XDG): вне редактируемого агентом рабочего дерева и вне исчезающего `/tmp`. Версионный корень (`…-v2.7.1`) позволяет держать предыдущую сборку для отката (п. 5.4).

Структура staged-пакета: `dist/` (скомпилированный JS), `prompts/reviewer-system.txt`, `index.ts` (entry-шим; host-факт: `plugins:[<dir>]` резолвит `<dir>/index.ts` и игнорирует `package.json main`), prod-`node_modules/`. Каталог дальше по тексту — `$PKG = ~/.local/share/opencode-llm-approval-v2.7.1/opencode-llm-approval`. В bash `~` разворачивается шеллом; в `opencode.json` (`plugins`) путь писать **абсолютным** (`/home/<user>/…`) — проверенные прогоны шли с абсолютным путём, разворачивание `~` в JSON-конфиге хостом не проверялось.

## 3. Guard-конфиг (глобальный, доверенный)

Путь: `~/.config/opencode-llm-approval/config.json` (схема `schemas/config.schema.json`; примеры — `examples/guard.shadow.json`, `examples/guard.auto.json`). Ключевые решения оператора:

- **mode**: `off` → `shadow` → `auto` (по лестнице квалификации п. 5; `auto` нельзя включить случайно — это отдельное сознательное редактирование).
- **model**: пара `providerID`/`id` из вашей действующей конфигурации OpenCode (провайдер подключается штатно; ключ плагину не нужен и не передаётся).
- **policy.autoAllow** — порог оператора. Настраиваемое: `maxRisk` (≤ MEDIUM), `minConfidence` (≥ MEDIUM), `allowedCategories` (без UNKNOWN). **Структурные потолки** (схемой, не обойти конфигом): HIGH/CRITICAL/UNKNOWN-риск, LOW-confidence, UNKNOWN-категория никогда не авторазрешаются. Консервативный старт: `LOW/READ/HIGH`. D7: `escalation.allowedCategories` — надмножество глобального набора, разрешает расширенные категории (например `EXEC`) только с вердикта ступени эскалации; вердикт primary с «лишней» категорией один раз откладывается цепочке.
- **policy.workspaceRoots** — корни, внутри которых guard работает вообще (cwd вне корня → ask без LLM).
- **policy.alwaysAskPathPrefixes** — чувствительные префиксы путей (локальный стоп до LLM).
- **privacy.allowCommandTransmission** — согласие на передачу текста команды модели. `false` = guard работает, но любая оценка заканчивается `PRIVACY_BLOCKED` → ask. В `shadow`/`auto` должно быть осознанное `true`; `destinationReview` — ваша запись, куда и на какой аккаунт уходит payload.
- **limits**: `hookDeadlineMs` 8000 (настраивается в 1000–120000; 120000 — зашитый максимум схемы и кода, конфигом не перезаписывается); `llmTimeoutMs` — потолок 30000 (дефолт 6500), закладывайте с запасом по латентности вашего провайдера (живые замеры оператора — локальный evidence) либо выбирайте более быструю модель ревьюера; `maxResources` — потолок 32 (дефолт 8): поднимайте, если безвредные команды с многими путями (git с pathspec, составные) стопятся `PAYLOAD_TOO_LARGE`; `maxInFlight` — потолок 8 (дефолт 2); бюджет цепочки `llmTimeoutMs + N × escalation.timeoutMs` обязан влезать в `hookDeadlineMs`; каждый TIMEOUT заканчивается безопасным `ask`. Превышение любого потолка даёт `CONFIG_INVALID` → guard полностью инертен (все ask, аудит молчит) — при тюнинге лимитов сверяйтесь с ceilings схемы и обновляйте dist вместе с конфигом.
- **audit.directory** — каталог вне рабочих деревьев; ошибка записи аудита → `ask` (автоапрув без аудита невозможен).

### 3.1. Ручное переключение режима через Visual Studio Code

1. Откройте в VS Code через **File → Open File** файл `~/.config/opencode-llm-approval/config.json` (или `code ~/.config/opencode-llm-approval/config.json`, если команда `code` доступна). В окне выбора файла `~` означает домашний каталог текущего пользователя.
2. Измените только значение поля верхнего уровня `"mode"`: `"off"`, `"shadow"` или `"auto"`. Например, `"mode": "shadow",`. Это строгий JSON: двойные кавычки, без комментариев и лишней запятой после последнего поля.
3. Сохраните файл. При желании проверьте синтаксис без вывода содержимого: `python3 -m json.tool ~/.config/opencode-llm-approval/config.json >/dev/null`.
4. В **OpenCode Desktop V2** после сохранения конфига перезагрузите плагин. Guard читает свой конфиг один раз при загрузке плагина, поэтому смена guard-конфига (как и смена `plugins`-записи) требует перезагрузки. Лёгкий путь: `opencode reload` (перечитать конфигурацию; фоновый сервер и сессии продолжают работать), затем проверить `opencode plugin list` — колонка SOURCE должна показать актуальный путь плагина. Если новая конфигурация не подхватилась — гарантированный путь из официальных доков: `opencode service restart` (рвёт текущие сессии — завершите запросы заранее; доки V2 предупреждают, что изменения вне наблюдаемых каталогов «may still require restarting OpenCode»). Закрытие одного окна Desktop само по себе не гарантирует перезагрузки сервера; если Desktop подключён к серверу на другой машине, перезагружайте именно тот сервер. VS Code перезапускать не нужно.

| Режим | Результат для входящего shell `ask` |
|---|---|
| `off` | Guard пропускает запрос без оценки; действуют нативные правила OpenCode. |
| `shadow` | При выполнении preflight и разрешённой передаче вызывает выбранную модель и записывает, **разрешил бы** порог команду или оставил бы `ask`. Реальный запрос остаётся `ask`. |
| `auto` | Только прошедший все gates и порог текущий `ask` может получить разовое `allow`; остальные остаются `ask`. |

Поля `model`, `policy.workspaceRoots`, `policy.autoAllow`, `privacy`, `audit` остаются самостоятельными настройками. `privacy.allowCommandTransmission: false` в `shadow` приводит к `ask/PRIVACY_BLOCKED` без вызова модели. Значение `true` разрешает передачу **всех подходящих запросов внутри перечисленных roots**, а не только команд, которые вы собирались вручную проверить. Перед включением сверьте provider/model/account, `destinationReview`, root и состав команд. Статус ограниченных live-проб и незавершённой квалификации `auto` приведён в [T13](TASKS.md); этот ранбук не фиксирует значения личного конфига оператора.

Файл `~/.config/opencode/opencode.json` управляет подключением плагина и нативными permissions отдельно. Нативные `allow` не проходят оценку guard, поэтому для проверки нужен действительно входящий `ask`. Не используйте режим хоста, который обходит permission-запросы.

### 3.2. Журнал `shadow` и оценка модели

Путь задаёт `audit.directory` в guard-конфиге. Откройте значение этого поля в своём `config.json`, затем файл `<audit.directory>/audit.jsonl`; при ротации появляются `audit-1.jsonl`, `audit-2.jsonl`. В примере лимиты составляют 5 MiB на файл и максимум три файла; действующие значения берутся из вашего конфига. Каждая строка — отдельный JSON-объект. В VS Code можно искать по `"mode":"shadow"`. Для наблюдения в терминале подставьте свой каталог аудита в `tail -f '<audit.directory>/audit.jsonl'`.

Смотрите поля `outcome` и `reasonCode` вместе:

| Запись | Значение |
|---|---|
| `shadow_would_allow` / `RISK_WITHIN_THRESHOLD` | Модель дала валидную оценку в пределах порога; guard **разрешил бы** текущий `ask` в `auto`. В `shadow` команда всё равно ожидает штатного решения человека. |
| `ask` / `RISK_ABOVE_THRESHOLD`, `CATEGORY_NOT_ALLOWED`, `CONFIDENCE_BELOW_MINIMUM` | Оценка не прошла настроенный порог; `ask` сохраняется. |
| `ask` / `PRIVACY_BLOCKED`, `OUTSIDE_SCOPE`, `MODEL_UNAVAILABLE`, `TIMEOUT` и другие коды | Оценки модели могло не быть; не считайте такие записи отрицательным вердиктом модели. |
| `skipped` / `NATIVE_ALLOW` | Хост уже разрешил команду по своим правилам; модель её не оценивала. |

Журнал содержит timestamp, локальный `requestID`, fingerprint входа, mode, outcome/reason, IDs модели, latency и версию policy. Он **не содержит** текст команды, cwd, ответ модели, его риск/категории/уверенность, prompt, ключи или transcript. Fingerprint использует случайную соль процесса, поэтому по одному журналу нельзя установить, какая именно команда дала запись, или сопоставить её между перезапусками. Даже `allow_prepared` в `auto` означает успешную запись до финальной проверки: это не доказательство применения `allow` либо исполнения команды хостом.

Для оценки качества модели проведите контролируемый `shadow`-прогон на отдельном тестовом root: заранее составьте безопасный размеченный набор команд, обеспечьте для них входящий `ask`, записывайте соответствие каждой пробы и её результата отдельно и сравнивайте с ожидаемым решением. Негативные сценарии можно подавать модели как **данные тестового harness**, не исполняя их как shell-команды. Другой модели можно дать агрегаты или вручную подготовленный обезличенный отчёт; один `audit.jsonl` позволяет оценить частоты исходов и ошибок, но не точность классификации по командам. Перед передачей даже минимального журнала внешней модели проверьте его содержимое и назначение данных.

## 4. Конфиг OpenCode (глобальный, ручное слияние)

Фрагмент-основа: `examples/opencode.global.fragment.jsonc`. Правила слияния:

- `plugins: ["$PKG"]` — путь на **каталог** (не файл); проверено на v2.0.18/2.0.19.
- `permissions`: широкое `{ "action": "shell", "resource": "*", "effect": "ask" }` ставится **перед** более узкими `deny` — побеждает последнее совпавшее правило. Свои deny не удалять; deny остаётся финальным для guard (хук на deny не вызывается).
- Не включать режимы хоста, обходящие permission-запросы, и не добавлять широкие `allow` поверх `shell:*` — иначе команды до guard не доходят.

## 5. Лестница квалификации и включение auto

Каждый шаг — только после записанного PASS предыдущего (аудит + события). Команды для прогонов — безвредные (`pwd`, `cat` одного файла проекта).

1. **off**: плагин загружен, аудит пишет `skipped/MODE_OFF`, нативные промпты не изменились.
2. **shadow + mock** (без сети и ключей): квалификация сборки на вашем хосте — скрипт `tests/manual/m4-harness-index.ts`: полный конвейер, исход `shadow_would_allow`, событие остаётся `ask`.
3. **shadow + live** (consent, `allowCommandTransmission: true`): небольшой безвредный корпус; ожидание — конформные оценки, `shadow_would_allow` только внутри порога. NOT_EVALUATED_LIVE-случаи записывать, а не ретраить до бесконечности.
4. **auto**: сменить `mode` на `auto`, перезагрузить OpenCode штатно. Positive/negative smoke: безопасная команда в пороге — исполняется (аудит `allow_prepared`); вне порога — остаётся штатный диалог (аудит `ask`).

### 5.4. Откат/обновление

- **Мягкий стоп**: `mode: "off"` в guard-конфиге + перезагрузка. Аудит продолжает писать `skipped`.
- **Аваритный стоп процесса**: env `OPENCODE_LLM_APPROVAL_DISABLE=1` — guard полностью инертен.
- **Снятие плагина**: удалить `plugins`-запись из конфига OpenCode. Персистентных permissions guard не создаёт — чистки allow-правил не требуется (ваши собственные правила не трогаются).
- **Обновление сборки**: сохранить прежний staged-каталог и пару версий (host/SDK), развернуть новый, пройти п. 5.1–5.4 заново на своей фактической версии хоста. Не переписывать весь конфиг и не удалять credentials. С 2.8.1 валидация `alwaysAskPathPrefixes` ужесточена: ранее молча принимавшиеся Windows-формы вида `a\..\b`, `..\x`, `\secrets` теперь дают `CONFIG_INVALID` (видно в warn) — перед обновлением приведите префиксы к `/`-форме (`\` нормализуется автоматически, обходные последовательности — нет).

## 6. Честные границы (что НЕ проверено/не гарантируется)

- Живой auto с реальной моделью не включался и не проверялся end-to-end (T11 — shadow; P1/P2 — mock). Включение — за оператором (T13).
- Live-распределение оценок модели по опасным подсказкам (MEDIUM+ на подсказках MEDIUM+) не измерялось — провайдер-латентность не позволила снять redirect/injection-пробы (локальный evidence T11).
- Отменённый хостом живой вызов генерации не settle'ится до конца процесса (наблюдение T11) — на безопасность не влияет, но тарификация отменённых запросов не гарантируется.
- Проверено на Ubuntu 24.04 / Linux; другие платформы — NOT_RUN.
- Guard не sandbox: защищает только запросы, дошедшие до permission-hook; врождённые `allow` и другие плагины с теми же правами — вне модели угроз (docs/04).
