# Перед реализацией

## Что уже решено

Нужен небольшой серверный плагин OpenCode V2, который вмешивается до штатного permission prompt. Модель выбирается независимо от основной coding-модели. Плагин использует настроенный в OpenCode provider; собственного хранилища ключей и provider registry нет.

Начальная ОС — Ubuntu 24. Другие ОС могут работать позже, но не должны считаться проверенными без собственного smoke. Защита держится на детерминированных отказах до LLM (секреты, scope, лимиты, binding) и пороге риска оператора: выше LOW — всегда человек, а потолки схемы не позволяют разрешить HIGH/CRITICAL/UNKNOWN.

## Что делать первым

1. Зафиксировать локальные `opencode --version` и `bun --version` либо фактическое имя установленного V2 бинарника. Ничего не переустанавливать поверх рабочей версии. Найти совместимую точную версию `@opencode/plugin`.
2. Прочитать `docs/03-opencode-v2-contract.md`. Подтвердить типы hooks, generation и связь полного tool input с permission source. Заполнить compatibility record.
3. Создать рабочий package, строгий TypeScript, mock тесты и плагин в режиме `shadow`; не включать его в рабочий профиль пользователя.
4. Пройти этапы M1–M5 из плана; операторские действия вывести отдельно, не симулировать их успешность.

## Минимально работающий срез

Входящий `ask` → mock reviewer → многомерная локальная валидация ответа → порог → `ask`. Затем тот же путь с live `ctx.generate.text`, но всё ещё shadow. Затем успешный live smoke и явное операторское переключение на `auto` для `graduated-v1` с консервативным порогом LOW/READ/HIGH-confidence.

Важно: shadow — не готовый функциональный релиз сам по себе. Реализация должна содержать полностью протестированный путь auto; включение на машине пользователя отделено от написания этого пути.

## Неизвестные данные пользователя

Точный build OpenCode, SDK version, provider/model ID, выделенный root, endpoint/account и API-ключ не предоставлены. Код не должен требовать их, чтобы пройти offline unit-тесты. В примерах используются `REPLACE_ME_*`; они должны отклоняться operational-валидацией и никогда не запускать fallback.

Чтобы использовать реальную LLM, оператор один раз выбирает provider/model, разрешает передачу минимальных данных и задаёт workspace root. Разработчик не подставляет «дешёвую модель по умолчанию».

## Приоритет результата

Сначала код, способный пройти mock-тесты и работать с настоящим SDK. Затем эксплуатационные удобства. Не добавлять daemon, dashboard, сложный CLI, расписание, интеграцию с Jira/GitLab или универсальный permission framework.
