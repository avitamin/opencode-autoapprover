# 06. Модель, payload и ответ

## Единственный transport MVP

`ctx.generate.text` с явно выбранным `model` через существующий provider OpenCode. Классификатор не меняет основную модель сессии, не вызывает tools, не создаёт сессий и не добавляет review в историю. Каждая модель эскалационной цепочки (D3) вызывается тем же stateless-вызовом; выбор ступеней — явная конфигурация оператора (`escalation`, docs/05), не решение модели или кода во время запроса.

Использовать существующий **допущенный API-key provider**, настроенный в глобальном/base контексте. API-ключ не копируется в config/логи/репозиторий guard. Если этот путь не работает на целевой сборке, fallback — ask с диагностикой; добавление собственного HTTP клиента — отдельное последующее решение владельца, не задача MVP.

Выбор модели делает пользователь; не хардкодить актуальные названия моделей из примеров документации. Желательные свойства: стабильный JSON, следование ограничениям, приемлемая latency и измеренная работа на negative corpus. Низкая temperature не является доказательством безопасности.

## Формирование prompt

Источник инструкции — `prompts/reviewer-system.txt`, встроенный в установленный пакет. Это название файла проекта, а не предположение о наличии `system` поля в API. При string-only API собрать trusted instruction + явное указание о недоверенности следующего JSON + сериализованный `ReviewInput`.

Не использовать интерполяцию payload в role markers, XML closing tags или executable template. Делать JSON serialization обычным безопасным сериализатором. Разделитель сам по себе не защищает от prompt injection; важны порог оператора и отсутствие инструментов.

Model DTO (`schemas/review-input.schema.json` v2) содержит version, полный raw command (составные команды передаются целиком), согласованные resources, cwd относительно root, локальное имя workspace и trusted local facts (binding/scope/приватность подтверждены). **Пороги оператора (`autoAllow`) в DTO не включаются**: модель оценивает риск честно, а не подгоняет ответ под желаемый порог.

Не включать descriptions инструмента, произвольную metadata, transcript, содержимое файлов, user messages, system secrets, полный env и абсолютные пути вне root. Не выполнять shell expansion. Если после такого ограничения невозможно понять действие — `UNKNOWN`, не догадка.

## Ответ: многомерная градация

Строгий JSON object по `schemas/assessment.schema.json` v2: `schemaVersion`, `risk`, `categories`, `confidence`, `signals`, `summary`. Семантика полей и связности — в `docs/04`. Нет boolean «approve everything», произвольных extra fields, ссылок на новые инструкции или tool calls.

Один ответ описывает сразу все аспекты оценки («разные вопросы» в одном запросе): уровень риска, категории действия, уверенность и замеченные сигналы. Уточняющих вопросов модель не задаёт. Единственная встроенная многоступенчатость — эскалационная цепочка D3: тот же DTO без изменений переотправляется следующей модели цепочки, если предыдущая вернула неконкретный результат (`UNKNOWN` risk / невалидный ответ / LOW confidence по флагам `escalation.triggerOn`). Конкретный вердикт, транспортный сбой и timeout никогда не переоцениваются; итог любой ступени проходит те же потолки.

Связность: любой опасный signal (`SECRET_LIKE`, `DESTRUCTIVE`, `PRIVILEGE`, `NETWORK_EGRESS`, `INJECTION_ATTEMPT`) требует `risk` ≥ `MEDIUM`; `risk=LOW` требует пустой `signals`; `risk=UNKNOWN` требует `confidence=LOW` и категорию `UNKNOWN`. Несогласованный ответ не исправлять; ask.

JSON должен быть единственным значением во всём ответе. Пробелы по краям допустимы; markdown fences, prose, два объекта, duplicate keys, NaN, comments, массив, строки вместо полей, отсутствующие/лишние поля, невалидный UTF-8 и сверхлимитный ответ → без repair: ответ либо окончателен, либо (по `escalation.triggerOn.invalidResponse`) переотправляется следующей модели цепочки как есть. Не вырезать «первую пару фигурных скобок» и не делать repair/retry внутри одной ступени.

Обычный `JSON.parse` не обнаруживает duplicate keys. Реализация должна дополнить его корректным обнаружением повторов либо использовать маленький проверенный parser с соответствующим режимом. Не писать распознавание JSON регулярным выражением. Schema validator и duplicate-key parser не должны выполнять код или загружать remote schemas.

## Отображение причин

`summary` предназначен для локальной проверки формата/тестов; не писать его в аудит и не показывать напрямую как доверенную инструкцию. UI message строится по закрытому набору `reasonCode` и local reason codes: например, «Автоодобрение не выполнено: риск выше порога оператора» или «Автоодобрение не выполнено: ответ модели неоднозначен». Это исключает управление терминалом или выдачу секретов через ответ модели.

## Таймаут и стоимость

Без эскалации — один вызов на допущенную оценку; с включённой цепочкой — не больше `1 + escalation.models.length` последовательных вызовов на событие, всегда внутри одного hook-бюджета. Скрытых fallback-моделей нет: каждая ступень названа в доверенном конфиге. Ступень эскалации не стартует, если до hook-дедлайна осталось меньше 1 000 мс; бюджет ступени клэмпится остатком. Сетевые запросы пропускаются для local-stop inputs. Rate limit и in-flight считаются на событие, а не на физический вызов: эскалация не расходует дополнительный слот.

Исследованный generation response не даёт оснований обещать точный token/USD budget. В MVP лимиты ограничивают число обращений, размеры и ожидание плагина. Внутренние retries/буферизация/стоимость provider runtime должны быть проверены на выбранной сборке и отражены в отчете. Не заявлять жёсткий денежный предел по одному только числу вызовов SDK; для него нужны лимиты на стороне провайдера.

После client timeout remote inference может продолжиться. Поздний результат не применяется, физический незавершённый запрос учитывается в in-flight лимите до settle. Если cancellation propagation неизвестна или появились зависшие запросы, открывается circuit breaker; новые запросы остаются ручными до безопасного восстановления/reload.
