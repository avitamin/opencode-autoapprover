# 01. Требования и границы релиза

## Цель

Уменьшить число ручных подтверждений обычных локальных операций, сохранив за пользователем решение об опасных, спорных и непонятных командах. Плагин не оценивает качество кода и не выполняет задачи.

## Функциональные требования

| ID | Требование |
|---|---|
| FR-01 | Загружаться как нативный V2 server plugin с default export и уникальным ID |
| FR-02 | Обрабатывать только входящие `ask` для действия `shell`; `allow`, `deny` и остальные actions не изменять |
| FR-03 | Получать полную исходную команду, cwd и связь с конкретным tool invocation; scanner resource не заменяет полный input |
| FR-04 | Передавать допущенный минимальный контекст явно выбранной оператором LLM через provider OpenCode; опциональная эскалационная цепочка (D3) добавляет до двух следующих моделей на неконкретный результат предыдущей ступени, а при заданном `escalation.allowedCategories` (D7) — на категорийный defer: конкретный вердикт в пределах риска/уверенности, не прошедший только глобальный категорийный набор |
| FR-05 | Только детерминированный маппинг оценки на порог оператора (`autoAllow`) может превратить текущий `ask` в `allow`: `risk<=maxRisk AND confidence>=minConfidence AND categories subset-of allowedCategories` при всех остальных gates |
| FR-06 | Риск выше порога, `UNKNOWN`-оценка, несогласованный ответ, ошибки и неподдерживаемые случаи сохраняют native prompt |
| FR-07 | Не создавать новых permanent/session permissions и не отвечать на другой pending request |
| FR-08 | Поддержать `off`, `shadow`, `auto`; безопасный первоначальный пример — shadow без разрешённой передачи данных |
| FR-09 | Отдельная пользовательская конфигурация, фиксированный reviewer model, порог `autoAllow`, workspace admission и always-ask exclusions |
| FR-10 | Минимальный локальный JSONL audit и детерминированные диагностические reason codes |
| FR-11 | Ограничить длительность, объемы, число параллельных и частоту оценок; автоматические повторы запрещены — единственное исключение: явно сконфигурированная оператором эскалационная цепочка (≤2 ступени) на неконкретный результат (`UNKNOWN` risk, невалидный ответ, LOW confidence по флагам) или, при заданном `escalation.allowedCategories`, на категорийный defer D7 (конкретный вердикт в пределах риска/уверенности, не прошедший только глобальный категорийный набор); вердикты, провалившие риск/уверенность, транспортные сбои и timeout не эскалируются |
| FR-12 | Обработать отмену, поздний ответ, unload, повторное событие, изменение snapshot и конкурентные запросы |
| FR-13 | Проверять точно поддерживаемую комбинацию host/SDK/platform; неизвестная комбинация не получает live auto |
| FR-14 | Работать без доступа к API в offline mock-тестах; live smoke вызывается отдельно и явно |

## Правила безопасности

| ID | Обязательное свойство |
|---|---|
| SEC-01 | Только `ask → allow`; нет автоматического `deny` |
| SEC-02 | Модель не может отменить локальную stop-condition и выйти за пределы порога оператора; потолки риски/confidence/категорий зашиты в схему конфигурации |
| SEC-03 | Secret/privacy check выполняется до обращения к LLM |
| SEC-04 | Snapshot запроса, policy, модели и корреляции неизменяемы для решения |
| SEC-05 | Никаких transcript, shell execution, credential extraction, writes в runtime policy |
| SEC-06 | In-flight результат после terminal/deadline никогда не меняет effect |
| SEC-07 | Ошибка аудита исключает auto-allow |
| SEC-08 | Нет широкого allow-cache, самообучающихся разрешений и доверия к прежним решениям пользователя |
| SEC-09 | Секреты, oversized/control-char input, несвязанный или неполный input и cwd вне root → ask без обращения к модели; составные команды оцениваются моделью в пределах порога |
| SEC-10 | Host bypass / конфликт approval-плагинов — unsupported deployment, а не повод угадывать безопасность |

## Первая версия

В первой активной версии применяется политика `graduated-v1`: любая shell-команда, дошедшая до `ask`, оценивается моделью по градуированной шкале (риск, категории, уверенность, сигналы); авторазрешение по умолчанию доступно только ответам `LOW / READ / HIGH-confidence` внутри допущенных roots. Составные команды участвуют в оценке наравне с простыми.

Оператор может расширить порог в пределах структурных потолков (`maxRisk` до `MEDIUM`, `minConfidence` до `MEDIUM`, добавление категорий `WRITE`/`EXEC`/`NETWORK`/`STATE_CHANGE`). Категорийное расширение возможно и только для ступеней эскалации: `escalation.allowedCategories` (надмножество глобального набора) — вердикт primary, не прошедший только глобальную категорийную проверку, один раз переотправляется цепочке, и расширенная категория автоапрувится лишь с вердикта ступени эскалации (D7). Расширение требует повторной оценки модели на негативном корпусе и обновлённого smoke; дефолт консервативен. Автоматическое разрешение целой сессии не вводится.

Не охватываются V1, MCP tools, отдельный клиент/интерфейс подтверждений, редактирование файлов, review-кода, поддержка всех shell/OS и произвольные повторные/уточняющие запросы к модели (единственное встроенное исключение — ограниченная эскалационная цепочка D3).

## Нефункциональные цели

По умолчанию общий бюджет hook — 8 000 мс; бюджет LLM — 6 500 мс внутри него. Общий бюджет настраивается оператором в диапазоне 1 000–120 000 мс: 120 000 мс — зашитый абсолютный потолок схемы и кода, который конфигом не перезаписывается. Ступень эскалации получает свой `timeoutMs` (дефолт 9 000, ≤30 000; потолок LLM-ступени — те же 30 000), суммарный бюджет цепочки должен влезать в hook-бюджет, и ступень не стартует, если до дедлайна осталось меньше 1 000 мс. Это целевая граница возврата управления, а не обещание realtime при зависшем event loop или ОС. Не больше двух физических незавершённых классификаций на экземпляр плагина (эскалация выполняется внутри уже занятого слота), 20 новых оценок за скользящие 60 секунд — эскалация не расходует дополнительный слот rate limit. Входная команда ≤4 096 UTF-8 bytes, до 8 resources (дефолт; потолок схемы — 32), review payload ≤8 192 bytes, ответ ≤8 192 bytes на каждую ступень.

Локальный preflight не обращается к сети и не запускает процессы. Допускаются только необходимые `stat`/`realpath` для проверки cwd/root binding: не читать содержимое рабочих файлов и не проверять файловые операнды команды. Документация не задаёт выдуманный порог точности LLM; критерий — ноль auto-allow на обязательном негативном корпусе при честных оценках `MEDIUM`+ и проверяемая полезность на позитивном.
