# OpenCode LLM Approval

**Комплект документации для реализации нативного плагина OpenCode V2.**
Дата исследования: **25 сентября 2026 года**. Версия комплекта: **2.0.0** (ревизия дизайна: градуированная LLM-оценка вместо recognizer, см. ADR-15).

Плагин сокращает ручные подтверждения команд: запрос, который OpenCode собирался показать пользователю, проверяется отдельной LLM. Только безопасная команда, прошедшая локальные ограничения, может получить разовое автоматическое разрешение. Опасность, неопределённость, ошибка или неподдерживаемый случай сохраняют обычный диалог OpenCode.

**Статус реализации (29.09.2026):** плагин реализован и проверен — 349 offline-тестов, packaged host smoke на opencode v2.0.18/2.0.19, синтетическая live-оценка в shadow с согласия оператора. Уровни готовности разделяются: **core ready** и **shadow pilot ready** — да; **auto pilot ready** — нет (включение auto — отдельное действие оператора, [T13 в TASKS.md](TASKS.md)). Операторская инструкция: [INSTALL.md](INSTALL.md); сводка приёмки: [reports/ACCEPTANCE.md](reports/ACCEPTANCE.md). Архив по-прежнему не содержит кода, который автоматически устанавливается, выполняет команды из fixtures или меняет ваши permissions.

## Принятые решения

| Вопрос | Решение проекта |
|---|---|
| Платформа | Только OpenCode V2; первоначальная приёмка на Ubuntu 24 / Linux |
| Реализация | TypeScript, Promise API нативного плагина; Bun для разработки и тестов |
| Перехват | `ctx.permission.hook("evaluate", ...)`; не автоматизация интерфейса |
| Модель | Одна явно заданная пара `providerID` / `id`, при необходимости `variant` |
| Доступ к LLM | `ctx.generate.text(...)` через существующий провайдер OpenCode |
| Ключ | Обслуживается OpenCode; плагин не читает его credential-файлы |
| Детерминированный слой | Нативные правила OpenCode + рекомендуемый deny-фрагмент; собственный command recognizer удалён |
| Оценка | Один многомерный ответ LLM: риск LOW–CRITICAL, категории, уверенность, сигналы |
| Решения плагина | Только оставить `ask` либо заменить текущий `ask` на `allow` по порогу оператора |
| Первый запуск | `shadow`: оценивать, но не разрешать автоматически |
| Первая активная версия | Политика `graduated-v1`: авторазрешение LOW/READ/HIGH-confidence, порог оператора `autoAllow` со структурными потолками |
| Сбой | Ручное подтверждение; никаких fallback-моделей и автоапрува при ошибке |
| Инфраструктура | Без сервера, БД, UI, MCP, очереди заданий и внешнего оркестратора |

Точные сведения о публичных API и ограничения исследования собраны в [источниках](docs/11-upstream-evidence.md). Собственные типы и схемы в этом комплекте — контракты **нашего проекта**, не якобы готовые SDK-типы OpenCode.

## Как начать

Распакуйте содержимое этой папки в новый репозиторий. Откройте репозиторий в OpenCode и передайте текст из [prompts/implement-in-opencode.md](prompts/implement-in-opencode.md).

Агент сначала читает [AGENTS.md](AGENTS.md), [START_HERE.md](START_HERE.md) и [план реализации](IMPLEMENTATION_PLAN.md). Остальные документы читает по текущему этапу, а не загружает весь пакет в каждый запрос.

Нельзя включать разрабатываемый auto-approval для собственной разработки плагина. Первые проверки проводятся на mock и в отдельном одноразовом тестовом каталоге; реальный ключ и переключение `auto` остаются действиями оператора.

## Важные границы

Плагин не является sandbox или гарантией безопасности произвольного shell-кода. Он не может защитить запрос, который хост вообще не передал в permission-hook, и не может противостоять вредоносному плагину с теми же правами процесса.

Встроенные `allow` остаются вне его проверки; существующие `deny` нельзя ослаблять. Поэтому для охватываемых команд базовая настройка — `shell: ask`, без широких разрешающих правил. Для удобства автоапрува нельзя включать режимы хоста, обходящие запросы разрешений.

Градуированная LLM-оценка вероятностна: одна и та же команда может получать разные вердикты, а prompt injection в аргументах атакует непосредственно оценивающего. Авторазрешение ограничено порогом оператора со структурными потолками (HIGH/CRITICAL/UNKNOWN и категория UNKNOWN неразрешимы схемой конфигурации), обязательным негативным корпусом, shadow-first и аудитом. Автоматического deny нет: спорные и опасные по оценке команды всегда возвращаются человеку.
